# 체계적 디버깅

증상을 추측으로 때우지 말고 **근본 원인**을 찾는다. fix를 쌓지 말고 한 번에 하나씩 검증한다.

## 1. 근본 원인 조사

- 에러 메시지·스택 트레이스를 **끝까지 정독**한다(요약하지 말 것).
- **재현** — 실패를 드러내는 테스트를 만들거나 `pnpm exec vitest run -t "<케이스>"`로 좁혀 재현한다.
  네트워크 변수는 MSW `server.use()`로 결정론화한다.
- **최근 변경 확인** — `git diff` / `git log`로 무엇이 바뀌어 깨졌는지 역추적한다.
- 콜스택을 따라 실제 실패 지점까지 내려간다(첫 에러 라인 ≠ 원인일 수 있음).

## 2. 패턴 분석

- **작동하는 유사 코드**(같은 레이어의 다른 슬라이스·훅)와 깨진 코드를 한 줄씩 비교한다. 차이가 곧 단서다.

## 3. 가설 → 검증

- 한 번에 **한 변수만** 바꿔 가설을 검증한다. 효과 없으면 되돌리고 다음 가설로.
- 여러 fix를 동시에 쌓지 않는다 — 무엇이 고쳤는지 알 수 없게 된다.

## 4. 수정

- 원인을 재현하는 **실패 테스트를 먼저** 만들고(→ test-driven-development 스킬) **단일 수정**으로 통과시킨다.
- **같은 증상에 3번 이상 실패하면** 개별 수정이 아니라 **아키텍처 / FSD 경계 · 상태 흐름 자체**를 의심한다.
